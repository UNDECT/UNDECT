# 갭 표 비판적 검토 + 수정본 (v2)

> 검토 대상: 로컬 Claude Code가 만든 `04-gap-table.md`(브랜치 `feel-pass-1-screenfx`)
> 이 문서는 코드를 직접 보지 않고 **갭 표의 논리**만 검토했다. 갭 표가 "있다/없다"로 적은 사실 판단은 그대로 믿었다.
> 목표 기준: "레퍼런스 인게임을 로블록스에서 최대한 똑같은 체감으로". 그래서 기준을 "기능이 있다"가 아니라 **"플레이하면 그렇게 느껴진다"**로 잡았다.

---

## A. 총평

갭 표는 전체적으로 잘 만들었다. 코드 근거가 있고, "새로 만들지 말고 키운다"는 원칙도 맞다. 다만 아래 **12곳**은 틀렸거나 그대로 진행하면 문제가 생긴다. 가장 큰 문제는 세 가지다.

1. **순서 의존성 오류**: UI 디자인과 오디오를 뒤로 미뤘다. 그런데 앞 Phase가 그 둘을 필요로 해서 **다시 만들어야 하는 작업**이 생긴다.
2. **키즈 규칙을 실제보다 좁게 해석했다**: 그래서 처치 손맛을 필요 이상으로 포기했다.
3. **이름 충돌**: 기존 "오버클록"(시간 감속)과 프롬프트의 "오버클럭"(RAM을 체력으로 대납)이 같은 이름이다.

## B. 잘못된 곳 / 약한 곳 12개

### ① 점수 재산정: 결론은 맞지만 근거가 "있다 = 점수"다
- 45~48점이라는 결론은 동의한다. 코드 기준으로 다시 매기면 **47점**이다(아래 C 참고).
- 하지만 갭 표는 "기능이 있으면 점수"로만 셌다. 레퍼런스 체감 기준으로는 **오히려 감점인 요소**가 있는데 빠졌다.
  - **둥근 키즈 패널 HUD**: 사이버펑크와 정반대 인상을 준다. 다른 것을 다 잘해도 화면 첫인상이 깨진다.
  - **고정 점 조준선**: 무기별 확산이 보이지 않아 총의 성격이 안 느껴진다.
  - **알림이 채팅창에 뜸**: 사이버 안구 HUD 느낌이 없다.
- → 이 세 가지는 "없음"이 아니라 **"있어서 감점"**으로 분류하고 우선순위를 올린다.

### ② 키즈 규칙 해석 오류: Mild 등급이 허용하는 것보다 좁게 막았다
- 갭 표: "키즈 설정(Mild)이라 처치 = 디지털 분해, 피·시체 없음."
- 로블록스 공식 기준([Content Maturity](https://create.roblox.com/docs/production/promotion/content-maturity))에 따르면:
  - **Minimal**: 가끔 나오는 약한 폭력, 약한 비현실적 피. Roblox Kids 계정이 접근할 수 있는 건 이 등급이다.
  - **Mild**: 더 잦은 약한 폭력, **더 많은 비현실적 피**. 폭력은 "결과가 비현실적이면 Mild"로 본다.
  - **Moderate**: 중간 수준 폭력, **약한 사실적 피**.
  - **Restricted**: 강한 폭력, 많은 사실적 피. 성인 신분 인증이 필요하다.
- 즉 지금 쓰는 "피·시체 없음"은 **Mild보다 엄격한 자체 규칙**이다. Mild 안에서도 다음은 가능하다.
  - **랙돌 → 분해**: 랙돌은 피도 아니고 시체 방치도 아니다. 맞은 방향으로 0.6~1.0초 날아가 쓰러진 뒤 기존 `DissolveService`로 분해하면 **규칙을 지키면서** 처치 무게감을 낼 수 있다. 갭 표는 랙돌을 피·절단과 한 묶음으로 막아 버렸는데, 이건 논리 오류다.
  - **절단 → "크롬 부품 이탈"**: 사이버 팔다리가 스파크·네온 냉각액(비현실적 색)과 함께 떨어져 나가고 바로 글리치 조각으로 분해된다. 세계관에도 맞고, 결과가 비현실적이다.
  - **피 → 비현실적 "데이터 출혈"**: 시안·마젠타 글리치 입자.
- ⚠️ 확인할 점: 의도가 "Roblox Kids 계정도 들어올 수 있게"라면 등급은 Mild가 아니라 **Minimal**이어야 하고, 그러면 지금 규칙이 맞다. **사용자 결정 사항이다**(D-Phase 0).
- 최종 등급은 개발자가 작성하는 설문으로 정해지고 모더레이션 판단이 따로 있다. 위 내용은 공식 문서 기준 해석이다.

### ③ 순서 오류 1: HUD 디자인 언어를 Phase 4에 둠
- Phase 1~3에서 새 UI를 많이 만든다: 쿨다운 링, 스캐너 정보 패널, 해킹 목록, 적 해킹 경고 바, 침투 미니게임 패널, 시술소 화면.
- 디자인 언어(사선 패널·모노 숫자·3색)를 Phase 4에서 정하면, 앞에서 만든 UI는 **둥근 키즈 스타일로 만들었다가 다시 만들어야 한다**.
- → **Phase 0에서 디자인 토큰을 먼저 확정**하고 공용 모듈(`UiTheme`: 색·폰트·패널 생성 함수·글리치 등장 함수)로 만든다. Phase 4는 "기존 HUD를 토큰으로 교체"하는 작업이 된다.

### ④ 순서 오류 2: 사운드를 Phase 7에 둠 → Phase 2를 끝낼 수 없다
- Phase 2의 완료 조건이 "화면·**소리**·카메라·HUD 4채널"이다. 그런데 오디오 소스는 Phase 7에서 정한다. 그러면 Phase 2는 **절대 완료될 수 없다**. 모순이다.
- → Phase 0에서 오디오 소스를 정한다. Phase 1에서 `SoundMix` + **SFX 레지스트리**(키 → 에셋 ID 표, 예: `ability.chrono.start`)를 만든다. 에셋이 아직 없으면 내장음으로 임시 매핑하되, 코드는 **키로만 호출**하게 한다. 그러면 나중에 에셋만 바꿔 끼우면 된다.
- 오디오 소스 선택지: 크리에이터 스토어의 로블록스 공식 라이선스 음원(무료, 바로 사용 가능) / 직접 업로드 / 둘 다. Phase 7은 음악·앰비언트 "완성"만 맡는다.

### ⑤ 이름 충돌: "오버클록" 두 개
- 기존 코드: `OverclockRules.worldTimeScale`, `OverclockPresentation`. 이건 **시간 감속** 기능이다.
- 프롬프트 §3-5 "오버클럭": **RAM이 모자라면 체력으로 대납**하는 사이버덱 기능이다.
- 갭 표는 이 둘을 같은 이름으로 나란히 적었다("사이버덱 오버클럭 ❌"). 이대로 구현하면 `overclock` 프리셋·변수·리모트 이름이 겹친다.
- → 체력 대납 기능은 다른 이름을 쓴다. 예: **"생체 연산"**(`BioCompute` / `HpForRam`). 프리셋도 `overclock`(기존 감속 층)과 `bioCompute`(청색 글리치)로 나눈다.

### ⑥ 자기모순: "이름 유지" vs "OverclockRules→TimeScale"
- "먼저 알아 둘 것 3번"에서는 이름을 유지한다고 했다. 그런데 Phase 1 표에서는 `OverclockRules`→`TimeScale`로 바꾼다고 했다.
- → 새 공용 모듈 `Shared/TimeScale`을 만든다. `OverclockRules`는 내부에서 `TimeScale`을 호출하는 얇은 래퍼로 남긴다. 그러면 **기존 테스트와 호출부를 깨지 않고** 일반화할 수 있다.

### ⑦ TimeScale 설계 빈틈 4가지
1. **서버/클라이언트 두 층을 구분하지 않았다.**
   - 서버 버블: NPC AI 틱, 애니메이션, 걷기 속도, 적 탄. 근처에 있는 다른 플레이어도 같이 느린 적을 본다.
   - 클라이언트 로컬 배율: 비, 비행차, 파티클, 주변 소리, 화면 효과. **사용자 본인 화면에서만** 느려져야 한다.
   - 갭 표에는 "적·적 탄·비·비행차"가 한 줄에 섞여 있다. 비·비행차가 서버 쪽 감속을 따르고 있다면 다른 플레이어 화면의 비까지 느려진다. 어느 쪽인지 확인한다.
2. **Humanoid 중력은 배율이 먹지 않는다.** 공중에 뜬 NPC는 감속 중에도 정상 속도로 떨어진다. → 버블에 들어오는 순간 속도에 `s`를 곱하고, 중력 보정 `VectorForce = 질량 × g × (1 − s²)`를 위로 건다. 버블을 나가면 원래대로 돌린다.
3. **겹침 규칙은 맞지만 의도를 적어 둬야 한다.** 협동 플레이어가 버블 안에서 싸우면 그 사람에게도 적이 느리게 보인다. 이건 "협동 보너스"로 받아들이고 문서에 적는다. PvP(3v3)에는 적용하지 않는다.
4. **잔상 비용.** 0.05초마다 캐릭터를 복제하면 초당 20개 모델이 생긴다. → 서버에서 만들지 않는다. **각 관찰자 클라이언트**가 미리 만든 고스트 6개를 링버퍼로 재사용한다. 저사양에서는 3개로 줄인다.

### ⑧ "Studio에서 하나씩 켜 보며 확인" — 규칙 위반 소지
- 프로젝트 규칙상 Claude는 Studio를 열 수 없다. 사용자가 확인해야 한다. 그런데 19종 프리셋을 일일이 상황을 만들어 켜 보는 건 비현실적이다.
- → **개발용 프리셋 미리보기 패널**을 만든다(Studio에서만 켜짐, `RunService:IsStudio()`). 프리셋 목록, 강도 슬라이더, 반복 재생, 두 프리셋 동시 재생(합산 확인)을 넣는다. 사용자는 패널만 눌러 보면 된다.

### ⑨ Phase 1이 너무 크고, 눈에 보이는 결과가 늦다
- 기반 7개를 다 만들어야 화면에 처음으로 변화가 생긴다. 방향이 틀렸으면 7개를 다 고쳐야 한다.
- → **수직 슬라이스 원칙**: Phase 1은 "기반 최소 + **크로노 하나를 완전체로**" 만든다. 크로노에 ScreenFx 새 레이어, CameraFx, SoundMix, TimeScale을 끝까지 붙이고 레퍼런스와 비교한다. 통과하면 같은 파이프라인으로 나머지 프리셋과 능력을 확장한다.
- `HighlightPool`은 크로노에 필요 없다. 스캐너(Phase 3) 바로 앞으로 옮긴다.

### ⑩ 완료 기준이 없다
- "효과 추가", "연출 전부" 같은 항목은 언제 끝났는지 판단할 수 없다. "완벽히"를 목표로 하면 **측정 가능한 완료 기준**이 꼭 필요하다.
- → 아래 수정 표에 "완료 기준" 열을 넣었다(시간 ms, 채널 수, 수치).

### ⑫ 사소한 것
- `hurt`(기존) vs `hit`(프롬프트) 이름 중복 → 기존 `hurt`를 유지하고 표에 매핑만 적는다. 이름을 바꾸면 테스트가 깨진다.
- `SoundMix`: SoundGroup + EqualizerSoundEffect도 괜찮다. 다만 먹먹함을 강하게 내려면 고음 −20dB, 중음 −8dB 정도는 필요하다. 새 Audio API(AudioEqualizer/AudioFilter + Wire)를 쓰면 저역 통과가 더 자연스럽다. 기존 `Sound` 객체와 섞어 쓰기 복잡하니 **SoundGroup 방식을 유지하고 수치만 키운다**.

## E. "완벽히 구현"에 대해 솔직하게

- **100% 똑같이는 불가능한 영역**이 있다(엔진 한계): 진짜 색수차·모션 블러, 실시간 바닥 반사, 전역 시간 정지, 사용자 셰이더. 이건 C/D 등급 대체 연출로 **체감 80~90%**까지 가는 것이 현실적인 최대치다.
- **키즈 등급은 엔진보다 큰 천장이다.** 레퍼런스의 폭력 표현은 성인 등급이다. Phase 0-1을 (b)로 고르면 "손맛"은 대부분 되찾지만 레퍼런스와 같은 잔혹함은 아니다. 이건 기술이 아니라 **방향 결정**이다.
- 그래서 "완벽"의 정의를 이렇게 잡는다: **레퍼런스의 모든 요소가 구현 항목에 대응되고(누락 0), 각 항목이 완료 기준을 통과한다.** 최종 점검표(프롬프트 §10)가 이 기준이다.
